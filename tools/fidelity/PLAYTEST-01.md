## 1–3. Transformation momentum (Gameplay)
Each case holds the movement input through the whole transform.

| Case | before | first step | mid-fold | mesh handoff | end of fold | end + 0.25 s | press → control | press → 90% speed |
|---|---|---|---|---|---|---|---|---|
| robot→vehicle, forward | 5.50 | 0.34 | 0 | 0 | 0 | 7.50 | 2.00 s | 2.17 s |
| robot→vehicle, angled W+D | 5.50 | 0.34 | 0 | 0 | 0 | 7.50 | 2.00 s | 2.17 s |
| vehicle→robot, cruise | 15.0 | 0.50 | 0 | 0 | 0 | 5.12 | 1.17 s | 1.42 s |
| vehicle→robot, angled | 15.0 | 0.50 | 0 | 0 | 0 | 5.12 | 1.17 s | 1.42 s |
| vehicle→robot, boost | 50.0 | 2.78 | 0 | 0 | 0 | 5.12 | 1.17 s | 1.42 s |
| standstill (both directions) | 0 | 0 | 0 | 0 | 0 | 0 | 2.00 / 1.17 s | — (PASS: no spurious motion) |

All speeds are horizontal, in m/s.

**Verdict: velocity is ZEROED at the press and then held at 0 for the whole fold.** It is not
replaced, clamped or lost at the handoff; there is nothing left to lose by then.
- **Cause 1:** `Character::beginTransform` sets `velocity_ = {0,0,0}` (`Character.cpp:32`).
- **Cause 2:** `PlayerController::handleInput` zeroes `moveForward/moveRight/wantBoost` while
  `isTransforming()`, so `CharacterMovement` brakes toward 0 with any velocity left.
- **Why the first step is not 0:** `handleInput` computes the intent before it calls
  `beginTransform`, so one step of acceleration leaks in (0.34 = 20.48 m/s² × 1/60;
  0.50 = 30 × 1/60; 2.78 = DashSpeed/DashDuration × 1/60).
- **After the fold:** the new form re-accelerates from 0.

The original transfer behaviour is **UNKNOWN**: FIDELITY lists "velocity transfer at transform
(currently zeroed)" as open. The checks therefore only assert "not a dead stop" (≥ 50% on the
first step, ≥ 25% minimum during the fold) as **KNOWN**, owner Gameplay.

**Additional CONF finding:** `Xe-TransGame.ini [TransGame.TnPawn]
_RestoreWeaponTransformFractionRemaining=0.75` ("1 = at the beginning of the transform, 0 = at
the end"). The original restores the weapon with 75% of the to-robot fold remaining. The rebuild
holsters it for the whole fold (`weapon_restore_frac_elapsed_to_robot` = 1.0 vs 0.25, KNOWN,
Gameplay).

## 7. Optimus vehicle materials (Rendering)
Objective checks; all PASS on integration:
- **Slots:** 2 authored slots == 2 GLB materials; names match (`Cust2_Mat_INST`, `InteriorAlt_Energon`).
- **Parent graph:** `CHR_Transformer_NormSpec_Cust_E_Mat`, the same master as the robot.
- **Textures:** all role textures (normal, emissive/Lum, mask/CustAB, Grunge) come from
  `TR_Optimus_VEH_p`, and the files exist.
- **Compiled render data:** both vehicle materials are present with GLSL. Each parameter chain
  starts at the vehicle's own MIC, no robot-package texture is bound, and the texture files exist.

**Most likely cause of "vehicle looks wrong": energon/emissive colour (Rendering).** The fixed
front-camera A/B stills (`work/fidelity/probe/int/still_vehicle_{wfc,legacy}.png`) show:
- **Legacy path** (AssetTools' bake of the customization shader): blue/cyan glow lines and a white
  Autobot logo.
- **WFC shader path:** the glow lines, wheel rims, exhaust stacks and logo all glow **red**. The
  robot's glows are red too (`startup.png`).

The two translations of the same material disagree:
- **AssetTools emissive bakes:** BLUE-dominant. Vehicle mean RGB (83,124,157) over 3507 bright
  texels; robot (89,133,168).
- **Compiled `CHR_Transformer_NormSpec_Cust_E_Mat` graph** (robot and vehicle): the only HDR
  colour constant is `vec4(1.25, 0.05, 0.05)`, which is **red**. It is masked by `AuxGlow.b`,
  scaled by `Energon_Intensity` and pulsed by `fractalMaps`, with `UseAutobotEnergonColor = true`.

`matc.py` maps StaticSwitch `true → A`, which matches UE3, so this isn't a trivial swap. The
energon colour branch (`UseNeutralEnergonColor` / `UseAutobotEnergonColor` and the LUT switches)
needs tracing in the original graph. Checked by `runtime-probe.ps1 -Sections materials`
(`material_consistency.*.energon_hue_bake_vs_compiled`, KNOWN, Rendering).

The vehicle **does** get its own parameters in GLSL: Cust_Color_A (0.599, 0.016, 0.016),
Cust_COLOR_B, Reflection 0.2, ColorBrightness 0.6, Specular 0.65, PowerDown 0.5. So "rendered
with the robot's values" is ruled out.

What differs from the robot (INFO, for the visual A/B):
- **Authored scalars:** 14 differ from the robot's. Examples:
  - ColorBrightness 0.6 (robot 1.5)
  - Emissive_Intensity 3 (robot 20)
  - PowerDown 0.5 (robot 1)
  - Reflection_Intensity 0.2 (robot 0.6)
  - Specular_Intensity 0.65 (robot 0.4)
  - customization colours A/B differ

  These values are baked into the vehicle GLSL (verified above).
- **Normal map:** the vehicle material compiles with `UseReconstructedNormal=true` (the robot's
  is false). `VH_Optimus_NORM` is **PF_DXT5** (the robot's is DXT1 RGB). The graph reconstructs
  `N = (A, G, sqrt(1-A²-G²))`, and the authored `UnpackMin` is **[-1,-1,-1, 0]**: G is remapped
  to [-1,1], alpha stays [0,1]. X would therefore never be negative, which skews vehicle
  lighting to one side.
  - The PNG itself is valid: UV islands are intact in R/G and A (visual check,
    `work/fidelity/matcheck/`).
  - Whether the 360 sampled DXT5 normal alpha with sign expansion is **UNKNOWN**. It's the top
    lead for Rendering, not a confirmed bug.
- **Stills for the visual A/B:** `still_vehicle_wfc.png` and `still_vehicle_legacy.png` (fixed
  front camera, same spawn), `still_robot_wfc.png`.

## New defect found while validating: input edges lost on zero-step frames (Gameplay)
The exe calls `PlayerController::handleInput` once per **render** frame and `applyToPawn` once
per **60 Hz step**. Above 60 fps, or with jitter, some frames run zero steps.
- **Reload:** `wantReload_ = wasPressed(Reload)` is re-assigned every frame. An R press on a
  zero-step frame is overwritten before it is applied.
- **Fire:** `wantFire_ = isDown(Fire)` behaves the same way, so a click shorter than one step
  never fires.

Jump is latched (`wantJumpLatched_`) and transform starts inside `handleInput`, so both survive.

The probe first hit this: the exe renders ~200 fps here, and the WFC_AUTORELOAD press was lost.
It is now deterministic in `wfc_fidelity` (`input_edges.*`, using `Rig::frameWithoutStep`):
- `reload_press_survives_zero_step_frame` — KNOWN
- `fire_tap_survives_zero_step_frame` — KNOWN
- jump and transform — PASS

Players will see this as an occasionally ignored R or a missed quick click.
